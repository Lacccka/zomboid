## Вердикт

Фокус: invites, accept/decline, membership, alliances and two-phase native faction mutations.

Combine this invite/confirmation pattern conceptually with QP Contracts' shared progress; do not bind quest parties directly to vanilla factions.

## Архитектура

| Слой | Что находится в слое |
|---|---|
| CLIENT | clan UI requests actions; receives InviteReceived/AllyRequest and Apply* instructions, then confirms native operations. |
| SERVER | validates owner/admin/membership/capacity, stores invites/alliances, expires pending work and reconciles vanilla Faction state. |
| SHARED | config and network constants are common; clan metadata is the shared wire model. |

## Network

- RequestData/Create/FinalizeCreate/CancelCreate
- Invite/RespondInvite/FinalizeJoin
- Leave/FinalizeLeave/Remove
- RequestAlly/RespondAlly/RemoveAlly
- ApplyCreate/ApplyNativeInvite/InviteReceived/ApplyJoin/ApplyLeave

Вывод по authority: серверный слой присутствует, но доверие проверяется по каждому handler отдельно.

## Persistence и identity

ModData store contains version, invites and per-clan records; reconciliation every 10 minutes and autosave/transmit every 15 minutes; pending create expires after 60 seconds.

## Полезные механики

- best invitation handshake reference
- server-side eligibility checks
- two-phase client/native mutation
- offline/persisted invitations
- reconciliation after partial failure

## Риски и anti-patterns

- some transient handshake tables are runtime-only
- native Faction is a second source of truth
- quest groups need immutable session IDs and explicit invitation expiry/replay protection
