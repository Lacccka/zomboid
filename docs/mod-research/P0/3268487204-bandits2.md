## Вердикт

Фокус: NPC brain/runtime, permanent agents, spawning, custom clans, AI programs and network synchronization.

Treat as an adapter boundary: our quest identity/session must remain stable even when the current Bandits zombie instance changes.

## Архитектура

| Слой | Что находится в слое |
|---|---|
| CLIENT | materializes and updates zombie-backed bandits, runs player-local rendering/interactions, requests spawns/restores and sends selected state changes. |
| SERVER | spawner/custom/server-command modules coordinate spawn, health, markers, vehicles and broadcast state. |
| SHARED | Bandit brain, programs, zombie actions, clans, scenes and data tables are shared between runtime sides. |

## Network

- modules Commands/Spawner/Sync/Custom/Players
- sendClientCommand/sendServerCommand
- brain/object ModData and transmitModData
- Global ModData clusters for persistent brains

Вывод по authority: серверный слой присутствует, но доверие проверяется по каждому handler отдельно.

## Persistence и identity

permanent brains are stored/restored through BanditPermanent and server spawner paths; identity is brain.id/uniqueId-like data, not the Lua object reference.

## Полезные механики

- our first-stage runtime
- permanent custom NPC lifecycle
- brain-to-zombie association
- custom clan/appearance data
- AI program extension points
- world marker and spawn protocols

## Риски и anti-patterns

- large mixed client/shared authority surface
- some actions originate from clients
- identity and restoration are sensitive to chunk unload/death/reconnect
- must track exact 42.20 API rather than older guides
